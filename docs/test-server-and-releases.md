# Test server and releases

Two servers run the same code with separate data:

| | Live | Test |
| --- | --- | --- |
| Worker | `health-api` | `health-api-staging` |
| Address | aurin.health (and petrfitnessdata.eu) | staging.aurin.health |
| Central database | `health-data` + 20 user databases | `health-data-staging` + 2 user databases |
| Food catalogue | `petrfitness-foods` | `petrfitness-foods-staging`; the read-only world catalogue in R2 is shared |
| Deployed by | `vydat.yml` (or `deploy-worker.yml` by hand, target production) | every push to main (`deploy-worker.yml`) |

Nothing is copied between them. The test server's pages carry a "TEST · staging" badge and
`X-Robots-Tag: noindex`; it sends no morning ops e-mail. Its `SESSION_SECRET` and `CONNECTION_KEY`
are generated by the first deploy and differ from the live ones, so a live session never works there.
Services it needs from outside (OpenAI, push, Google) are Worker secrets set by hand on
`health-api-staging`; without them those features are off there.

## The app

One TestFlight build serves both groups. The app talks to the live server unless an internal tester
switches it in Nastavení → Testování → Server (`ios-native/Loadwise/Data/ServerChoice.swift`). The row
shows for the owner and the e-mails in the live Worker's secret `INTERNAL_TESTERS` (comma separated),
and for everyone on the test server (`internalTester` in `/app/api/me`, `src/staging.js`). Each server
keeps its own session cookie and its own Apple Health last sync; passkeys work only on the live server
(the app's associated domain).

## Releasing: "Vydat"

Merges reach the internal TestFlight group (every build, with its pull request's notes) and the test
server. `vydat.yml`, run by hand:

1. picks the newest build uploaded from main, or the number typed in;
2. deploys the newest main to the live server (migrations, shards, smoke tests). Production only
   ever takes commits on main (deploy-worker.yml refuses others), so a release never puts back an
   older server than a hand-started deploy left there. Without a typed build number it stops when
   main has app changes the newest build lacks;
3. writes "What to Test" from the TestFlight sections of every pull request since the build the
   external group already has, adds the build to the external group (`EXTERNAL_GROUP` repository
   variable when there is more than one) and submits it to Apple's beta review.

A server-only fix goes live with `deploy-worker.yml`, target production, without a release.
