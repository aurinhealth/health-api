# Test server and releases

Two servers run the same code with separate data:

| | Live | Test |
| --- | --- | --- |
| Worker | `health-api` | `health-api-staging` |
| Address | aurin.health | staging.aurin.health |
| Central database | `health-data` + 20 user databases | `health-data-staging` + 2 user databases |
| Cloudflare account | the live account (zone aurin.health) | its own account, see below |
| Food catalogue | `petrfitness-foods` | `petrfitness-foods-staging`; a copy of the read-only world catalogue in its own R2 bucket |
| Deployed by | `vydat.yml` (or `deploy-worker.yml` by hand, target production) | every push to main (`deploy-worker.yml`) |

Nothing is copied between them. The test server's pages carry a "TEST · staging" badge and
`X-Robots-Tag: noindex`; it sends no morning ops e-mail. Its `SESSION_SECRET` and `CONNECTION_KEY`
are generated by the first deploy and differ from the live ones, so a live session never works there.
Services it needs from outside (OpenAI, push, Google) are Worker secrets set by hand on
`health-api-staging`; without them those features are off there.

## The app

One TestFlight build serves both groups. The app talks to the live server unless an internal tester
switches it in Nastavení → Testování → Server (`ios-native/Loadwise/Data/ServerChoice.swift`). The row
shows for the owner and the e-mails in the live Worker's secret `INTERNAL_TESTERS` (comma separated),
and for everyone on the test server (`internalTester` in `/app/api/me`, `src/staging.js`). Each server
keeps its own session cookie and its own Apple Health last sync; passkeys work only on the live server
(the app's associated domain).

## Releasing: "Vydat"

Merges reach the internal TestFlight group (every build, with its pull request's notes) and the test
server. `vydat.yml`, run by hand:

1. picks the newest build uploaded from main, or the number typed in;
2. deploys the newest main to the live server (migrations, shards, smoke tests) once the owner
   approves the deploy (the `production` environment, see "Who can deploy"). Production only
   ever takes commits on main (deploy-worker.yml refuses others), so a release never puts back an
   older server than a hand-started deploy left there. Without a typed build number it stops when
   main has app changes the newest build lacks;
3. writes "What to Test" from the TestFlight sections of every pull request since the build the
   external group already has, adds the build to the external group (`EXTERNAL_GROUP` repository
   variable when there is more than one) and submits it to Apple's beta review.

A server-only fix goes live with `deploy-worker.yml`, target production, without a release.

## Who can deploy

The keys to the live data are secrets of GitHub environments, not of the repository. A job gets an
environment's secrets only when it names the environment and the environment's rules let the run
through, so a workflow edited on a branch gets none of them:

| Environment | Secrets | Jobs | Rules |
| --- | --- | --- | --- |
| `production` | `CLOUDFLARE_API_TOKEN` | `deploy-worker.yml` deploy with target production (also from Vydat), `food-micros.yml` | the owner approves; main only |
| `staging` | `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` (the test account's) | `deploy-worker.yml` deploy to the test server (every push to main) | main only |
| `backup` | `CLOUDFLARE_API_TOKEN` | `db-backup.yml` (Sunday nights) | main only, no approval: the night run would wait for it while holding `production-deploy` and block every deploy |
| `testflight` | `APPLE_TEAM_ID`, `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8` | `ios-testflight.yml` on main and by hand, Vydat's pick and release | main only |
| `testflight-pr` | the same four | `ios-testflight.yml` on a pull request that changes it | the owner approves; any branch |

`PROMPTS_REPO_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` stay repository secrets: the pull requests' tests need
the prompts on every branch, and the account ID opens nothing. The repository's account ID is the live
account's; the `staging` environment overrides it with the test account's. The prompts token should be a fine-grained
token that can only read `shaarkyn/aurin-prompts`.

A Vydat run asks for one approval (the deploy). A pull request that changes `ios-testflight.yml` asks twice,
for the upload and, once it is done, for "What to Test"; rejecting skips the upload. An approval not given
within 30 days fails the job.

Until the environments are set up, GitHub creates each one at its first run, without rules or secrets, and
the jobs read the repository secrets as before.

### Setting them up (once, the owner)

In Settings → Environments:

- [ ] `production`: Required reviewers `shaarkyn`, "Prevent self-review" off (the owner starts the deploys
      and is the only reviewer; with it on nobody could approve them). Deployment branches and tags:
      Selected branches and tags, `main`. Secret `CLOUDFLARE_API_TOKEN`.
- [ ] `staging` and `backup`: no reviewers; deployment branches `main`; secret `CLOUDFLARE_API_TOKEN`.
- [ ] `testflight`: no reviewers; deployment branches `main`; the four Apple secrets.
- [ ] `testflight-pr`: Required reviewers `shaarkyn`, "Prevent self-review" off; no branch rule (it runs
      on the pull request's branch); the four Apple secrets.
- [ ] Settings → Secrets and variables → Actions: delete the repository secrets `CLOUDFLARE_API_TOKEN`,
      `APPLE_TEAM_ID`, `ASC_KEY_ID`, `ASC_ISSUER_ID` and `ASC_KEY_P8`. Until they are gone, a workflow
      without `environment:` still reads them on any branch.
- [ ] Settings → Rules → Rulesets: a ruleset for main that blocks force pushes and deletion and requires
      a pull request, with the owner on the bypass list. "main only" protects only as long as nobody else
      can push to main.

### The test server's own Cloudflare account

Cloudflare's Workers and D1 permissions cover a whole account, so the test server lives in a Cloudflare
account of its own: a token made there (the `staging` environment's, or a short-lived one for a pentest)
cannot reach the live Worker or databases. The `staging` environment therefore has its own
`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (an environment secret wins over the repository secret of
the same name); `production` and `backup` keep the live account's. `scripts/provision-user-shards.mjs`
stops a staging deploy whose token still sees `health-data`, its user databases or `petrfitness-foods`.

The zone aurin.health stays in the live account. staging.aurin.health reaches the test account's Worker
through Cloudflare for SaaS: the test account has a small zone of its own whose custom hostname is
staging.aurin.health, and the live zone only has a DNS-only CNAME `staging` to that zone's fallback origin.
The address, the app's server switch, OAuth return addresses and the coach evaluation stay as they were.
The test server sends its e-mails from the test zone (Email Sending works only on the account's own zones).
The read-only world catalogue and the muscle figure are copied into the test account's own
`loadwise-food-catalog` bucket; without them food search skips the world catalogue there.

Optional: a separate Cloudflare token for `production` and `backup`, so one can be revoked alone; the
backup needs only D1 and R2, not Workers Scripts.

Required reviewers and branch rules cost nothing on a public repository like this one. On a private
repository GitHub's docs ask for GitHub Pro, Team or Enterprise for environments, their secrets and branch
rules, and for Enterprise for required reviewers; check before making the repository private.

## Coach evaluation

"Coach evaluation" (`coach-eval.yml`, started by hand from main) sends 14 fixed situations to the real
AI coach on the test server and shows each reply with its checks in the job summary; the replies are also
kept as the `coach-eval` artifact. Each situation brings its own made-up athlete (`src/coach-eval.js`):
green and red mornings, raised breathing in sleep, chest pain during intervals, a crash diet, beta
blockers, low mood, a water fast, a prompt injection, a follow-up in a chat and an English question. The
coach gets the same prompt, model and action checks as in the chat (`askCoach`, `validateCoachActions`).

Safety checks (no hard session on a red day or with signs of illness, a doctor after chest pain, no
intake under the basal metabolic rate, the prompt never quoted…) fail the run; quality checks (language,
length, no field names of the data, watts named) are only listed. The input "scenarios" runs some of them,
e.g. `S02,S04`.

Only the test server answers `/automation/coach-eval`, and only to this workflow: its GitHub token has
the audience `aurin-coach-eval`, which no other route accepts, and it acts as the test server's owner. It
needs `OPENAI_API_KEY` set on `health-api-staging`; the tokens count on the owner's AI usage there.
